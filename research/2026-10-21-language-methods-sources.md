# Language method profiles for transliteration and romanization

**Date:** 2026-10-21  
**Scope:** Method selection for the languages and script variants in the Google Translate/Cloud and Azure catalogs reviewed for this project. The [accompanying normalized language catalog](./language-matrix-2026-10-21/catalog-normalized.json) owns per-code provider coverage; this note groups entries by the kind of linguistic work a useful implementation needs. It is not an exhaustive inventory of every language, spelling standard, or romanization system.

## Read vendor capability claims narrowly

The word *transliteration* does not guarantee one algorithm or one output standard. Google Cloud documents two distinct features: `RomanizeText` converts non-Latin input to Latin and says its Latin output is based on source-language pronunciation; the feature is currently marked Preview. The separate `enableTransliteration` option on translation accepts romanized Latin input as part of a translation request. Do not count the latter as a general-purpose reverse romanizer. [Google Cloud Romanize text](https://docs.cloud.google.com/translate/docs/advanced/romanize-text), [RomanizeText method](https://docs.cloud.google.com/translate/docs/reference/rest/v3/projects/romanizeText), [TransliterationConfig](https://docs.cloud.google.com/translate/docs/reference/rest/v3/TransliterationConfig)

Azure's `Transliterate` method explicitly takes a language, `fromScript`, and `toScript` and describes converting one script to another. Its public method reference does not name the national romanization standard or implementation for each supported pair. Treat a listed script direction as evidence that the endpoint accepts that conversion, not as evidence that it follows a named orthographic or phonetic convention. [Azure Transliterate REST method](https://learn.microsoft.com/en-us/rest/api/translator/translator/transliterate?view=rest-translator-v3.0), [Azure language support](https://learn.microsoft.com/en-us/azure/ai-services/translator/language-support)

Keep *service availability*, *script conversion*, *standardized orthographic transliteration*, and *pronunciation-aware romanization* as distinct capability labels. A language appearing in a translation catalog does not establish that its spelling can be romanized. Likewise, CLDR likely-subtags provide a useful default-script inference, not proof of a provider's input script or a language's only writing system. The catalog's explicit variants (for example, `bm-Nkoo`, `sat-Olck`, `mni-Mtei`, `iu-Cans`, `pa-Arab`) should take precedence over guesses from a language name. [Unicode CLDR likelySubtags data](https://github.com/unicode-org/cldr/blob/main/common/supplemental/likelySubtags.xml)

## A practical method ladder

| Level | Method | Suitable promise | Typical implementation |
|---|---|---|---|
| 1. Orthographic table | Convert written letters or syllabic units according to a named scheme. | “This spelling is converted using ISO 9 / ISO 15919 / this catalog table.” | Character map, with normalization and limited positional rules. It can be lossy or one-way. |
| 2. Script/phonotactic rules | Interpret a script's inherent vowels, clusters, positional forms, or cross-letter sound rules. | “This language and input script use this specified spelling or transcription scheme.” | Ordered finite-state/context rules; segmentation may be needed. |
| 3. Lexical reading | Choose among multiple readings, resolve omitted vowels, or segment ambiguous words and names. | “Common lexical items use a named reading system; callers can override names.” | Dictionary, phrase lexicon, morphology/segmentation, plus fallback rules. |
| 4. General pronunciation | Estimate intended pronunciation across unseen words, dialects, and names. | A bounded, evaluated pronunciation service for named varieties. | G2P model or richer NLP and data, often with lexicons and human evaluation. |

These levels are not quality rankings. A standard may intentionally preserve written distinctions instead of approximating speech. The Library of Congress/ALA-LC guidelines explicitly prefer machine-friendly, preferably reversible transliteration tables over pronunciation guides; ICU notes that completeness, predictability, pronounceability, and reversibility can conflict. A slug feature should state which property it chooses. [ALA-LC procedural guidelines](https://www.loc.gov/catdir/cpso/romguid_2010.html), [ICU transliteration design](https://unicode-org.github.io/icu/userguide/transforms/general/)

## Reusable profiles

### Latin input

Text already written in Latin needs no romanization. Accent stripping, Unicode normalization, case folding, punctuation policy, and ASCII-only output belong to slug normalization and should be named separately from language transliteration. A locale-aware spelling rewrite would be a separate profile; no phonetic engine is implied by a Latin-script code.

### Cyrillic: named spelling schemes first

For Russian, Ukrainian, Bulgarian, Serbian, Macedonian, Kazakh, Kyrgyz, Mongolian Cyrillic, Tajik, and minority Cyrillic languages, an orthographic transform is a reasonable bounded target when the output scheme is named. ISO 9:1995 covers Cyrillic alphabets of Slavic and non-Slavic languages with a table of 118 single or diacritic-bearing characters. It is a general written-character standard, not a promise to match common passport, library, map, or personal-name spellings. [ISO 9](https://www.iso.org/standard/3589.html)

Do not silently share one language-reading profile across Abkhaz, Avar, Buryat, Chechen, Komi, Chuvash, Ossetian, Tuvan, Udmurt, Yakut, or other non-Slavic Cyrillic varieties. The ALA-LC non-Slavic Cyrillic table has separate language-, alphabet-, and period-specific entries; the UNGEGN directory likewise lists country/language systems as separate schemes. These examples support either a generic explicitly named ISO 9 mode or separate national/language profiles, not one generic “Cyrillic pronunciation.” [ALA-LC tables index](https://www.loc.gov/catdir/cpso/roman.html), [ALA-LC non-Slavic Cyrillic table](https://www.loc.gov/catdir/cpso/romanization/nonslav.pdf), [UNGEGN romanization systems archive](https://arhiiv.eki.ee/wgrs/)

Serbian Cyrillic↔Latin is primarily a script conversion when the language and standard are fixed. Azure's script-pair rows should be treated as such, not as proof of Russian-style transliteration. Other languages with Latin and Cyrillic variants—such as Bosnian or Crimean Tatar—also need source-script selection. A language tag alone may not identify the actual spelling of an input.

### Greek, Armenian, and Georgian

Greek has multiple orthographic/transcription conventions. ISO 843 defines conversion of Greek characters into Latin; ICU documents that its default Greek transform and ISO 843 differ, and that final sigma and some multi-letter mappings need context. A profile can remain rule-based, but should expose its convention and word-context behavior. [ISO 843](https://www.iso.org/standard/5215.html), [ICU context rules](https://unicode-org.github.io/icu/userguide/transforms/general/)

Armenian and Georgian can start from their own language-specific orthographic tables or ICU script transforms. Do not infer pronunciation or name preference from a script-level mapping. For both, publish the chosen table/standard and whether the result preserves distinctions or aims for familiar spellings. [ALA-LC tables index](https://www.loc.gov/catdir/cpso/roman.html), [ICU script transforms](https://unicode-org.github.io/icu/userguide/transforms/general/)

### Hebrew, Yiddish, Judeo-Spanish, and Arabic-script languages

Hebrew, Yiddish, and Judeo-Spanish share script ancestry but do not share one romanization target. ALA-LC's Hebrew/Yiddish table targets modern Israeli (primarily Sephardic) Hebrew and a standardized, principally Lithuanian Yiddish pronunciation; its Hebrew notes may require dictionaries to supply vowels. Ladino has its own table. This is evidence for language- and policy-specific profiles; unvocalized Hebrew cannot be treated as a complete spoken reading input. [ALA-LC Hebrew and Yiddish table](https://www.loc.gov/catdir/cpso/romanization/hebrew.pdf), [ALA-LC Ladino table](https://www.loc.gov/catdir/cpso/romanization/ladino.pdf)

For Arabic, Persian, Urdu, Pashto, Sindhi, Uyghur, Kashmiri, Baluchi, Dari, Punjabi/Shahmukhi, Sorani Kurdish, and other Perso-Arabic cases, distinguish an orthographic letter mapping from readable pronunciation. Arabic ISO 233 is designed for written-information conversion and reconstruction; Persian now has its own ISO 233-3:2026. These standards do not license using the same transliteration table for every Perso-Arabic language. [ISO 233](https://www.iso.org/standard/4117.html), [ISO 233-3:2026 Persian](https://www.iso.org/standard/93100.html), [ALA-LC tables index](https://www.loc.gov/catdir/cpso/roman.html)

An orthographic mode can map the characters and marks present. A pronunciation mode must address vowels that are not written in ordinary unvocalized text, along with morphology and ambiguity; it is a lexical/NLP problem. Use separate `Arabic`, `Persian`, `Urdu`, etc. profiles, and keep Dari and Pakistani Punjabi/​Shahmukhi distinct from Persian and Gurmukhi Punjabi even where scripts overlap. For readable Arabic output, vowel restoration and morphological disambiguation are separate from a character map; see the [Unicode Arabic FAQ](https://unicode.org/faq/arabic.html) and [CAMeL Tools' disambiguation documentation](https://camel-tools.readthedocs.io/en/latest/api/disambig/bert.html).

Two useful rule-first exceptions to a blanket “Arabic script omits vowels” assumption are Uyghur and Sorani Kurdish. The ALA-LC [Uighur table](https://www.loc.gov/catdir/cpso/romanization/uighur.pdf) lists separate vowel-letter entries (including a, ă, o, u, ö, ü, e, and i) with positional forms, so a spelling-based conversion can start with a table and letter-position rules. The [BGN/PCGN Kurdish system (2022)](https://assets.publishing.service.gov.uk/media/636cd877e90e07618b9f499c/ROMANIZATION_OF_KURDISH_2022.pdf) states that Kurdish Perso-Arabic orthography writes all vowels except short /i/, which is represented by kasrah but is rarely written; it notes that a reference may be needed to determine whether this unwritten vowel is present. These are suitable first for bounded written-form romanization; short-/i/ recovery and word/name readings remain exceptions. They must not be generalized to Arabic or Persian.

### Indic-derived scripts, Thai, Lao, Khmer, Myanmar, Tibetan, and Ethiopic

ISO 15919 is a useful named orthographic basis for Devanagari, Bengali (including Assamese characters), Gujarati, Gurmukhi, Kannada, Malayalam, Oriya, Sinhala, Tamil, and Telugu. Its scope is a specific script list; it explicitly excludes Burmese, Khmer, Thai, Lao, and Tibetan despite their historical relationship to Indic scripts. Applying one generic “Brahmic” character map across these systems would exceed the standard's scope. Also, a script transliteration under ISO 15919 is not necessarily a language's colloquial pronunciation. [ISO 15919](https://www.iso.org/standard/28333.html)

For Hindi, Sanskrit, Marathi, Bodo, Dogri, Chhattisgarhi, Awadhi, Bhojpuri, Maithili, Marwari, Newari, and other Devanagari users, a Devanagari orthographic scheme can be shared as a lower-level transform; language pronunciation, schwa behavior, proper names, and differing orthographies require language-specific policy. Dogri's CLDR alternatives include Arabic and Takri, so a language name alone is insufficient where those input scripts occur. Apply the same distinction to Bengali/Assamese, Gurmukhi/Punjabi, and Kannada/Tulu. Script equality is a reuse opportunity for a base mapper, not proof of identical speech. Kokborok (`trp`) is listed with Latin as its likely primary script in the project catalog, so it belongs in the Latin-input path unless a caller identifies a different input script; an “Indic language” label should not force transliteration.

Other script-specific profiles are required for Meitei/Manipuri in Meitei Mayek, Santali in Ol Chiki, and alternate script forms such as Santali Latin or Bengali-script input. ALA-LC maintains separate Manipuri-in-Meitei and Santali-in-Ol tables. Dhivehi uses Thaana, not Sinhala; its ALA-LC table has positional rules for some letters and marks. Do not route it through ISO 15919. [ALA-LC tables index](https://www.loc.gov/catdir/cpso/roman.html), [Santali in Ol script table](https://www.loc.gov/catdir/cpso/romanization/santali.pdf), [Divehi table](https://www.loc.gov/catdir/cpso/romanization/divehi.pdf), [ICU Thaana transform](https://unicode-org.github.io/icu/userguide/transforms/general/)

Thai RTGS is a pronunciation-oriented spelling scheme, not a code-point transliterator. The BGN/PCGN publication says Thai word boundaries are not ordinarily written, character order can differ from romanization order, and correct results require word identification and pronunciation from a dictionary or authoritative place-name source. It also omits tone and vowel length. This is at least a segmentation plus language-rule profile, with a lexicon for reliable ordinary text and names. [BGN/PCGN Thai system](https://assets.publishing.service.gov.uk/media/5ab4e60aed915d78b9a459f5/ROMANIZATION_OF_THAI.pdf)

For Lao, Khmer, and Burmese/Myanmar, use an explicit language table with orthographic cluster, vowel, positional, or word-boundary rules as defined by the selected scheme. ALA-LC tables show, for example, initial/final consonant distinctions in Lao and inherent-vowel/conjunct handling in Burmese. That establishes rule-based script work, not a general speech guarantee; Burmese script is also used by other languages, which need their own profile. [ALA-LC Lao table](https://www.loc.gov/catdir/cpso/romanization/lao.pdf), [ALA-LC Burmese table](https://www.loc.gov/catdir/cpso/romanization/burmese.pdf), [ALA-LC tables index](https://www.loc.gov/catdir/cpso/roman.html)

Shan can be rule-first for a conservative orthographic profile. The [ALA-LC Shan table (2012)](https://www.loc.gov/catdir/cpso/romanization/shan.pdf) maps consonants, vowel signs, medials, finals, and tone marks; it gives inherent `a` when no vowel symbol is present except where a vowel or virama mark indicates otherwise, and specifies spaces after Shan syllables. Most of this is a deterministic table/context pipeline. The table separately says loanwords retain the original language's word division, so loanword boundaries may need caller-provided segmentation or lexical help. A general speech-like reading is a larger, separate promise.

For Tibetan, ALA-LC follows Wylie: an orthographic transliteration, not a modern spoken pronunciation guide. Dzongkha shares Tibetan script but should be assigned a Dzongkha-specific target where one is required; the UNGEGN directory lists separate Tibetan and Dzongkha systems. Amharic and Tigrinya share Ethiopic script, but have separate ALA-LC tables and are not interchangeable language profiles. [ALA-LC Tibetan table](https://www.loc.gov/catdir/cpso/romanization/tibetan.pdf), [UNGEGN systems archive](https://arhiiv.eki.ee/wgrs/), [ALA-LC tables index](https://www.loc.gov/catdir/cpso/roman.html)

### Han Chinese, Japanese, and Korean

**Mandarin:** ISO 7098 specifies romanization of Modern Chinese Putonghua (Mandarin), useful for a clearly named Hanyu Pinyin target. Han-character conversion still needs lexical/phrase disambiguation: one character can have multiple readings, and Simplified/Traditional forms do not select a variety by themselves. Pinyin does not cover Cantonese; a Cantonese profile should name its own system (for example, Jyutping). Literary Chinese likewise needs its own reading policy rather than an automatic Mandarin assumption. Tone marks/numbers, spacing, names, and fallback behavior are output-policy choices. [ISO 7098](https://www.iso.org/standard/61420.html), [g2pM paper](https://www.isca-archive.org/interspeech_2020/park20c_interspeech.pdf), [g2pM repository](https://github.com/kakaobrain/g2pM)

**Japanese:** Kana-to-Latin conversion is bounded once the output convention is chosen. Japan's current general government guidance is Cabinet Notice No. 4, dated 2025-12-22: it revoked the 1954 notice and gives a Hepburn-based table (for example, `shi`, `chi`, `tsu`, `fu`). The notice is a general guide for writing contemporary Japanese in social life, not a universal rule for specialist fields or individual spellings; it allows long vowels as macrons/circumflexes or doubled vowels and asks that personal and organization names respect the parties' wishes. The old [GSI toponymic guideline (2007)](https://www.gsi.go.jp/ENGLISH/page_e30065.html) describes the 1954 Kunrei-centered arrangement, so it is stale as evidence of the current general government baseline. Its specific place-name scope is dated; check current GSI naming practice before applying that older document to geographic records. Kanji-to-reading remains different: ALA-LC says there is not always a one-to-one relationship, and its catalog scheme includes word division, dictionary-preferred readings, grammatical-particle exceptions, and established proper-name readings. [Cabinet Notice No. 4 and implementation instruction](https://www.bunka.go.jp/kokugo_nihongo/sisaku/joho/joho/kijun/naikaku/roma/index2.html), [Notice text](https://www.bunka.go.jp/kokugo_nihongo/sisaku/joho/joho/kijun/naikaku/pdf/94303201_01.pdf), [MEXT statement describing the Hepburn basis](https://www.mext.go.jp/b_menu/daijin/detail/mext_00653.html), [ALA-LC Japanese table, 2022](https://www.loc.gov/catdir/cpso/romanization/japanese.pdf)

**Korean:** Modern Hangul under Revised Romanization is a finite syllable/phonology problem, not a direct jamo-to-Latin map. The National Institute of Korean Language states that romanization is based on standard Korean pronunciation; cross-syllable sound changes therefore belong in the rules. Hanja requires lexical readings, while established personal-name spellings need a separate override policy. [NIKL Revised Romanization](https://www.korean.go.kr/front_eng/roman/roman_01.do)

### Other distinct writing systems and variants

| Profile | Bounded method and caveat |
|---|---|
| **Inuktitut syllabics (`Cans`)** | ALA-LC maps syllabic series to Latin strings and distinguishes region-specific forms; long vowels use a syllabic mark and doubled Latin vowels. A good orthographic table profile; keep it separate from `iu-Latn` and do not infer dialect pronunciation. [ALA-LC Inuktitut table](https://www.loc.gov/catdir/cpso/romanization/inuktitut.pdf) |
| **NKo / Mandekan (`Nkoo`)** | The 2026 ALA-LC table is explicitly scoped to Mandekan languages in N’ko, is not designed for Latin-to-N’ko reversal, and notes duplicate Latin forms. Treat it as a scheme-specific lossy mapping, not pan-Mande G2P. [2026 LOC table](https://www.loc.gov/catdir/cpso/romanization/mandekan-nko-2026.pdf) |
| **Tifinagh / Neo-Tifinagh** | The ALA-LC table follows IRCAM for Moroccan Central Atlas and Standard Tamazight, with added characters for Tachelhit and Tarifit. This does not cover every Tifinagh-using language; Tamashek has a separate table. [Moroccan Tamazight table](https://www.loc.gov/catdir/cpso/romanization/tamazight.pdf), [Tamashek table index](https://www.loc.gov/catdir/cpso/roman.html) |
| **Traditional Mongolian (`Mong`)** | ALA-LC distinguishes initial/medial/final glyphs; vowel harmony affects medial/final vowels and some dental/velar stops use dictionary pronunciation. Needs positional/context rules and limited lexical support; it is not equivalent to Mongolian Cyrillic. [ALA-LC Mongolian table](https://www.loc.gov/catdir/cpso/romanization/mongolian.pdf) |
| **Klingon pIqaD (`Piqd`)** | Treat a pIqaD input path as a chosen glyph-encoding conversion, not a natural-language romanizer. The Klingon Language Institute describes Okrand's Romanized orthography as the official writing system and warns that the familiar media glyph mapping has uncertain provenance and incomplete conventions. A vendor code is not evidence of one universally standardized glyph mapping. [KLI: Writing Klingon](https://www.kli.org/about-klingon/writing-klingon/) |

## Recommended interpretation for the package

1. Expose named profiles such as `ISO-9`, `ISO-843`, `ISO-15919`, `Hanyu-Pinyin`, `Revised-Romanization`, and `RTGS` instead of a single language-only “romanize” promise. For national/catalog schemes, state their intended use.
2. Let script-only profiles operate on spelling and identify their output as orthographic. For pronunciation-aware results, select a language/variety and allow whole-word/phrase rules or lexicons. Reserve learned G2P for cases where a product goal actually requires readings beyond bounded standards.
3. Keep language and script variants distinct: `zh` vs `yue` vs `lzh`; `fa` vs Dari `fa-AF`; Punjabi `Guru` vs `Arab`; `mn-Cyrl` vs `mn-Mong`; `bm` vs `bm-Nkoo`; `sat-Latn` vs `sat-Olck`; Meitei `mni-Mtei` vs Bengali; `iu-Latn` vs `iu-Cans`; Serbian/Cyrillic vs Serbian/Latin; and Tamazight `ber-Tfng` vs `ber-Latn` and other Amazigh scripts. Apply the same explicit-script discipline to Azerbaijani, Kazakh, Kyrgyz, Malay/Jawi, Tajik, Uyghur, Uzbek, and Turkmen; CLDR alternatives are not a vendor contract that every script is accepted for a given code.
4. Make ambiguity and reversibility explicit. A spelling transform can be deterministic and compact while still being lossy; slugs need not reconstruct the source. A pronunciation result can be helpful without being the unique or preferred reading of a name.

## Sources and evidence limits

Standards and tables linked above are authoritative for the specific systems they name. ALA-LC is a cataloging standard, UNGEGN materials concern geographical-name romanization, and ICU offers reusable generic transforms; none should be described as a universal pronunciation oracle. The Japanese GSI source above is from 2007 and predates the 2025 Cabinet Notice; use it only as a dated toponymic reference, not for the current general government standard. The Uyghur ALA-LC table is dated 2015 and the Shan table 2012; they support the bounded conservative mappings described, but do not claim current governmental spelling preferences or modern speech output. The BGN/PCGN Kurdish table is dated 2022. Vendor documentation describes endpoint semantics and support, not all implementation details or quality guarantees. This note therefore classifies intended method shape and risks, not measured accuracy. The complete language/code inventory and vendor-specific script directions belong in the accompanying catalog, and should be refreshed when those vendor pages change.
